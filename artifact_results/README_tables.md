# FPS Result Tables

This directory contains committed representative outputs generated from request-level replay. No paper values are entered manually.

## One-command reproduction

From the artifact root:

```bash
bash scripts/run_all.sh
```

The command regenerates the deterministic FPS candidate experiments, distributed propagation-delay experiments, raw event CSVs, metadata, figures, and LaTeX-ready tables.

To regenerate only the FPS candidate tables:

```bash
python3 scripts/run_fps_experiments.py --requests 50000 --seed 2026
```

## Primary paper table: `baseline_comparison.csv`

Generated by `scripts/run_fps_experiments.py`.

It compares four operational approaches over the same 50,000-request replay for two candidates:

- **Unsafe candidate:** removes three permissions that are exercised by legitimate replay requests. Full SOR withholds promotion.
- **Safe candidate:** removes one entitlement generator-labeled redundant and exercised only by low-frequency stale accesses. Full SOR promotes it.

Columns:

- `Candidate`: safe or unsafe candidate policy.
- `Approach`: immediate enforcement, shadow-only validation, SOR without rollback, or Full SOR.
- `Proposed Reduction %`: stable-policy entitlements removed by the candidate.
- `Enforced Reduction %`: candidate reduction actually placed into force after the approach completes.
- `Legitimate Denials`: oracle-required requests denied by the enforced decision.
- `LDR`: legitimate-denial rate, computed as `Legitimate Denials / 50,000`.
- `Affected IDs`: distinct subjects with enforced legitimate denials.
- `Mismatches`: stable/candidate decision differences over the complete replay. The count is identical across approaches for the same candidate because candidate evaluation is held constant; enforcement behavior differs.
- `Safety Action`: `None`, `Shadow only`, `Promotion withheld`, or `Promoted`.

## Secondary table: `replay_prefix_sensitivity.csv`

Generated by `scripts/run_fps_experiments.py`.

This is a deterministic replay-prefix check, not a calendar-time observation-window experiment. Values represent shadow-evaluation outcomes, not enforced denials.

Columns:

- `Candidate`: safe or unsafe candidate.
- `Replay Prefix`: fraction of the complete replay.
- `Agreement S`: stable/candidate agreement over the prefix.
- `Mismatches`: decision differences over the prefix.
- `Candidate Would-Deny`: oracle-required requests the candidate would deny if enforced.
- `Candidate LDR`: `Candidate Would-Deny / Request Count`.
- `Candidate-Affected IDs`: distinct subjects that the candidate would deny.
- `Request Count`: explicit denominator.

## Propagation-delay table: `delay_sensitivity.csv`

Generated by `scripts/simulate_distributed_run.py` through `bash scripts/run_all.sh`.

It reports the deterministic three-node simulation for 500, 3,000, and 7,000 ms propagation-delay conditions. The table is separate from the 50K candidate replay.

## Thresholds and seed

Exact parameters are stored in `fps_experiment_metadata.json`:

- seed: `2026`
- request count: `50,000`
- observation prefix: `20%` (`10,000` requests)
- minimum gate observations: `20`
- mismatch-rate threshold: `0.03`
- legitimate-denial threshold: `0`
- candidate-expansion threshold: `0`

All FPS candidate results are a single deterministic paired replay, not averages across seeds. Confidence intervals and significance tests are therefore not reported.

## Oracle and metric semantics

The stable policy is the effective pre-remediation state, not the oracle. A request is required only when its `(subject, action, resource)` tuple is allowed by `datasets/examples/policy_required.json`.

A candidate mismatch is not automatically an enforced denial. `LDR` counts only required requests actually denied by the enforced decision. Candidate expansions are separately gated and must be zero in the current experiment.

## Raw outputs

`results/raw/fps_replay_events.csv` contains one row for each candidate, rollout approach, and request. Important columns include:

```text
request_id,candidate,approach,phase,subject,action,resource,
stable_decision,candidate_decision,enforced_decision,oracle_required,
mismatch,candidate_would_deny_required,legitimate_denial,safety_action
```

## Synthetic-data scope

The replay and reference oracle are synthetic. The safe candidate is safe only relative to the explicit generator-defined required-policy oracle. The replay exercises the removed redundant tuple, but this remains a synthetic construction. The artifact does not claim that absence from a synthetic replay proves redundancy in a real enterprise deployment.


## Scale sensitivity: `scale_sensitivity.csv` and `scale_sensitivity_summary.csv`

Generated by `scripts/run_sensitivity_experiments.py`. The per-seed file contains
nine rows: three scales times three deterministic seeds. The summary file reports
mean and range of observation-prefix mismatch rates and confirms the Full SOR
action at each scale. Raw events are in `results/raw/scale_sensitivity/`, and
generated policy snapshots are in `results/generated_scale_policies/`.

The small scale reuses the bundled primary policy structure and replay vocabulary.
The medium and large scales use a transparent generator declared in
`config/sensitivity_experiments.json`. These experiments test control-loop
behavior under increasing cardinality, not production realism.

## Threshold sensitivity: `threshold_sensitivity.csv`

This table recomputes the primary observation gate for mismatch-rate thresholds
0.005, 0.01, 0.03, 0.05, and 0.10. Required-denial and candidate-expansion
thresholds remain fixed at zero. The unsafe candidate is withheld at every row
because its observation prefix contains oracle-required would-deny events. The
safe candidate is withheld only at the strictest mismatch threshold.
